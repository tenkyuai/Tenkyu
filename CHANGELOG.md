# Changelog

All notable changes to Tenkyu. Versions follow semantic versioning once 1.0 is out; until then anything may change between 0.x releases.

## 0.3.0 (2026-11-28)

Night 2 (2026-11-27). Detection v2, a way to measure shadow mode, and the hosted service's first-week path. All benchmark figures are on synthetic data.

Library: persona-review fixes (privacy, a network cap, consistent examples)

- **Breaking:** `PostgresStore` now refuses to start without `key_secret` (it raised no error before and stored raw emails, IPs and device ids as keys). Pass `key_secret=os.environ["TENKYU_KEY_SECRET"].encode()`, or `allow_raw_keys=True` for a throwaway database or a test. The README and `docs/shared-store.md` examples pass a secret from an environment variable. The hosted service already did.
- **Breaking for the log format:** `DecisionLog(path, secret=...)` keys `email_hash` with HMAC-SHA256 (32 hex characters); without a `secret` there is no `email_hash`, because an unkeyed hash lets anyone confirm a guessed email. `tenkyu report` shows "not tracked" for repeat inboxes when the log has no hashes. Old logs (an unkeyed 16-hex hash) still read, and `shadow-report` and `evaluate` are unaffected.
- New default rule `network_daily_cap`: past 30 full grants in 24 hours from one /24 (IPv4) or /48 (IPv6) network, a signup that would be `allow` becomes `review` (partial credit). It never blocks, only counts decisions that stay `allow`, and is set with `Guard(network_daily_cap=...)` (`None` turns it off). On the held-out benchmark (20 seeds, `Guard()`): farmers flagged 79.9% and blocked 61.3% (unchanged), honest flagged 4.6% to 5.2%, honest blocked 1.2% (unchanged). With a cap of 20 honest flagged would be 6.8%, nearly all from the 80-person campus group; 30 was chosen.
- Docs: the README says that unkeyed SHA-256 hashes of guessable values (phone numbers) can be checked and recommends `link_secret` and `key_secret`; example free grant is $3 everywhere (it is the customer's own setting; the hosted dashboard pre-fills $5.00 for new accounts); version reads 0.3.0.dev0 and the README says PyPI has 0.2.1.

Library: detection v2 (figures in `docs/heldout-benchmark.md` and `benchmarks/FROZEN-v2.md`)

- New signals `lookalike_domain` (0.75) and `mixed_script_email` (0.50) in `tenkyu.lookalike`, using a bundled subset of the Unicode TR39 confusables table (`data/confusables.txt`). Domains that imitate a big provider are flagged: Cyrillic or Greek letters (`gmаil.com`), `0` for `o`, one typo, and `.com` typos such as `gmail.con` and `gmailc.om`. The address is still not merged with the real one, so the Cyrillic look-alike is no longer an undetected limit, but it is still a different address.
- New signal `obfuscated_email`: invisible characters hidden between Latin letters 0.75, fullwidth letters 0.6, other invisible or fullwidth characters 0.3, made-up subdomains of a known provider 0.6.
- New signal `device_farm` (0.75): 6+ accounts on one device in 7 days across 3+ /24 networks. A shared device on one network (school lab, family) stays soft `device_reuse`.
- New soft signals `wide_spread` and `regular_timing` (`tenkyu.proxy`) for rotating residential proxies; they count only next to a real signal. New soft signals `odd_domain` and `domain_burst` (`tenkyu.domains`); `domain_burst` alone never costs credit.
- Crowd rule: a clean, distinct identity (plain address at a big provider, a school or a normal-looking own domain, normal browser, no other signal) behind a busy IP gets partial credit (`review`), never a block, up to 60 signups an hour and 200 a day per IP. Past that the IP rules apply in full again. Worst case measured for one IP: about 17 grants an hour.
- Yahoo matching is limited to real Yahoo domains; `yahoo.attacker.xyz` is no longer treated as Yahoo.
- Benchmarks: the night-1 held-out set (seeds 1-20) was tuned on and is now a tuning set (farmers flagged 70.2% to 77.7%, blocked 38.5% to 54.9%, honest blocked 1.4% to 1.2%). On the blind v2 set (seeds 101-120, run once after the rules were frozen): farmers flagged 52.8% to 65.0%, farmers blocked 24.6% to 43.6%, honest blocked 12.5% to 1.6%, honest flagged unchanged at 20.4%. Rotating proxies (34%), shared-VPN farmers (32%) and unlisted disposable domains (46%) did not improve.
- Known limits added: a word-like catch-all domain spread over many networks is allowed; rotating residential proxies with a fresh device, inbox and IP each time stay hard; a school behind one IP gets partial credit for nearly everyone.
- With the crowd rule, a school of 60 signing up in 20 minutes went from 58 blocked to 6 on the tuning set.

Library: measuring shadow mode

- `tenkyu shadow-report LOG [LABELS]`: reads a `DecisionLog` and a labels CSV (`decision_id,label`) and prints precision, recall, honest users wrongly flagged and credit withheld, judged on what Tenkyu would have done in shadow mode. It warns under 50 labelled decisions, or when the labels cover only one kind of user. `--template OUT.csv` writes a labels file to fill in. Exit code 2 means the log or labels file could not be used.
- `tenkyu evaluate --decisions export.csv` scores recorded decisions (the hosted labelled export, with `action`, `would_action`, `shadow` and `label` columns) instead of replaying signups. It is chosen automatically when the file has an `action` column and no email or ip column. `-1` and `1,5` are not read as labels.
- `DecisionLog` lines carry a random `decision_id`. The first version derived it from a hash of the line, which let someone confirm a guessed email against it. Lines written by older versions get a derived id so old logs still work. Log lines with wrong-typed fields are skipped, and the template's cells are safe to open in a spreadsheet.
- `docs/first-week.md`: a day-by-day plan for shadow mode, labelling and reading your accuracy.

Recipes and JS client

- Recipes in `examples/`: `supabase-edge-function` (a Deno Edge Function with a browser snippet and the `credits` table SQL) and `vercel-nextjs` (a Next.js App Router route). Both create the account first, call Tenkyu only for a new account, grant credits by `credit_fraction`, and return the same `{ok: true}` for new, existing and blocked sign-ups. Tests run in Deno with no network. They have not run on a real Supabase or Vercel project.
- JS client (`clients/js`): when Tenkyu cannot be reached or answers with something that is not a valid decision, `check()` now returns a 25% grant (`failOpenCreditFraction`, default 0.25), not a full one. A decision flagged `degraded` is capped the same way. One deadline covers the first try, the 429 wait and the retry. The package ships its `LICENSE`. Set `failOpenCreditFraction: 1` for the old behaviour.

Hosted service

- Shadow mode by default. A new customer is in shadow mode for 7 days (`customers.shadow_until`, migration `0009_shadow_default.sql`); older customers are not. Live keys get `action: allow` and `credit_fraction: 1.0` plus `shadow`, `would_action` and `would_credit_fraction`. Test keys are never shadowed. The owner ends it with "Switch to live now" in Settings, extends it up to 30 days from today, or lets it run out. Decisions and Review rows are tagged, and shadow rows are left out of the review count.
- Dashboard first-run checklist: create a test key, add Tenkyu to your sign-up, see the first check. The Python snippet it shows grants credits by verdict after the account exists, with a small fail-open grant.
- Labels and "Your accuracy" (migration `0010_labels.sql`): label a decision farmer, real or not sure with one click, or upload a CSV (`decision_id,label`, up to 10,000 rows and 1 MB). Farmer and real labels use the same path as outcomes, so the shared network still learns only through the eligible-reporter rules. "Not sure" labels never reach the network. The accuracy page counts only live decisions you labelled, warns under 50 labels, and judges shadow decisions on `would_action`. A labelled CSV export has no emails, IPs or device ids. Uploads are limited to six per customer in ten minutes, one at a time per customer, and at most half the database pool at once per process (5 with the default of 10 connections).
- `python -m hosted.deploy.preflight`: a deploy rehearsal on a throwaway local database. It checks the environment, migrations, an in-process boot with one check, the audit-page build, the Dockerfile and the pinned requirements, then prints the deploy checklist. It never prints a secret value. See `hosted/deploy/README.md`.
- Fixes found by attack rounds: the preflight no longer prints passwords inside URLs, and label operations take locks in one order, so concurrent labels cannot deadlock or lose a network report.
- New dependency for the hosted API: `python-multipart` (label uploads).

## 0.2.2 (unreleased)

- `BlindStore(inner, secret)` wraps any store (Memory, SQLite, Postgres, your own) so it never holds a raw email, IP or device id: the variable part of every key and every stored value is HMAC-SHA256'd with `secret` (hex, 32 characters), and the kind before the first ":" stays readable. `PostgresStore(..., key_secret=...)` does the same inside the Postgres store. Decisions are identical to an unblinded store (tested on the held-out benchmark, every row). Stores now have `blind(value)`: the identity for the plain stores, the keyed hash for blinded ones. `Guard` applies it to every raw value it compares with `values()` results (the current email in `device_reuse` and `pattern_emails`, the `"plain"` marker). A custom store without `blind()` keeps working unchanged. `values()` of a blinded store returns blinded values.
- `PostgresStore(None, connection=conn)` borrows an open autocommit psycopg connection (for example from a pool) instead of opening its own; it does not create the table, sweep on open, reconnect or close it.
- `network_day` now counts only when another risk signal also fires for the same signup (alias or link reuse, device reuse, IP burst, disposable email, headless agent, any custom signal), so a busy university or mobile-carrier /24 no longer pushes honest users to review. A shared device (`device_reuse`) does not count as that other signal. `network_burst` changed too, see below.
- `Guard(link_secret=...)` (bytes, at least 16): link values are stored as HMAC-SHA256 instead of plain SHA-256. Without it, the first signup that carries `links` on a Guard warns once that phone numbers and similar low-entropy values can be reversed. Changing the secret stops old links from matching.

Fixes from the 2026-11-26 red-team run:

- A shared device on a busy network no longer blocks. `device_reuse` and `network_*` signals do not count as the "other" risk signal that switches `network_day` (and the 5+ burst tier) on, and when the only signals that fire are `device_reuse` and `network_*` the action is at most `review`. A family's second device-sharing account on a carrier /24 went from block to review (credit 0.25); a lone shared device was already review.
- `network_burst` on its own now needs 15+ signups from one network in 10 minutes (it was 5). With another real risk signal on the same signup (alias or link reuse, disposable email, headless agent, IP burst, any custom signal; not `device_reuse`, not `network_*`) the old 5+ tier applies. A campus /24 with 200 honest signups over 8 hours went from 110-120 signups in review to under 5%.
- Alias first, then the owner: the plain address is still never blocked for an alias someone else made, but it now gets action `review` (credit 0.25) with the reason "plain address after earlier alias signups of the same inbox: partial credit (2 accounts per inbox)" instead of a full allow. Without this, one inbox yielded two credited accounts. The `owner_after_aliases` signal still scores 0. Tests and the dashboard demo engine that expected a full allow were updated.
- `normalize_email` and `is_plain` apply Unicode NFKC first, then remove every format character (category Cf, which includes the soft hyphen U+00AD and bidi marks), U+034F (combining grapheme joiner) and variation selectors. `john@ｇmail.com` is `gmail.com`, `x@mailin\u00adator.com` is `mailinator.com` (and flagged disposable), `a@gm\u034fail.com` is `gmail.com`. Look-alike letters from other scripts (Cyrillic) are not mapped; see Honest limits.
- Link values are normalized before hashing, on both the plain and the HMAC path: NFKC, case-folded, whitespace, invisible characters and `- . ( ) _` removed. Phone-like names (see the phone bullet below) keep digits only (any script's decimal digits), so `+1 (415) 555-0100` and `14155550100` match. **Link keys stored by 0.2.1 (and by earlier 0.2.2 builds) for values containing spaces, capitals or punctuation will not match 0.2.2 keys**, so such an account can use its card or phone once more after upgrading. Values that were already lowercase letters and digits are unchanged. Side effect: two ids that differ only by `-`, `.` or `_` are now one link.
- `Guard` drops a port from `1.2.3.4:5000` and `[2001:db8::1]:443` before keying the IP (the same parser `signup_from_request` uses, now shared in `tenkyu.signals.host_of`). IPv6 signups are also grouped per /48 for `network_burst` and `network_day`, like an IPv4 /24, so rotating /64s inside one /48 no longer dodges them.
- A supplied but malformed email is now `block` (credit 0, reason "email address is not valid") instead of `review` with 0.25 credit. `python -m tenkyu score` exits with 20 for it. A missing email (None, "" or whitespace only) is not malformed: it produces no email signal at all and the other signals still apply, so phone-auth users from Clerk (`signup_from_clerk` gives `email=None`) and Supabase (`email ""`) are not blocked. A string that cannot be encoded as UTF-8 (a lone surrogate such as `"a\ud800@x.com"`) counts as malformed.
- Email merges, in addition to the Gmail and Yahoo rules: `anything@user.fastmail.com` (and `.fm`) is `user@fastmail.com`; `me.com` and `mac.com` are `icloud.com`; `protonmail.com`, `protonmail.ch` and `pm.me` are `proton.me`. **Stored history from 0.2.1 for those domains will not match the new keys**, so an address that signed up under the old form can sign up once more after upgrading.
- Softness comes only from the built-in signals: a custom `extra_signals` function that returns a signal named `device_reuse` or `network_*` is scored, counted as an "other" risk signal and can block like any custom signal; before, it was treated as soft by its name.
- A device id, IP or other free text that is not UTF-8 encodable (a lone surrogate) is keyed by its SHA-256, so `check` no longer raises `UnicodeEncodeError` inside `SQLiteStore`.
- The `link_secret` notice no longer raises out of `Guard.check` when warnings are errors (`-W error`, pytest `filterwarnings = error`); it goes to the `tenkyu` logger instead.
- The disposable-domain check walks the domain's parent suffixes against the set instead of scanning the whole list (same results).
- Phone links: names containing `phone`, `mobile` or `sms` (or `tel` as a word, e.g. `tel`, `phone_tel`) compare by digits. A leading `00` counts like `+` and a `(0)` trunk marker is dropped, so `+44 (0)20 7946 0958`, `+44 20 7946 0958` and `0044 20 7946 0958` are one link. National formats (`050...` versus `+97250...`) cannot be matched without a country: pass provider-verified E.164 numbers.
- Device ids are stripped of surrounding whitespace before keying; an id that is empty after stripping counts as no device id.
- The user-agent check matches whole tokens instead of the substring "bot", so Android CUBOT phones are no longer sent to review. `Googlebot`, `bingbot`, `bot/1.0`, `HeadlessChrome`, `python-requests`, `curl` and `wget` still match.
- Benchmark: the economics run builds card ids so honest and farmer ids differ by more than a separator (link values now ignore `-`); results are unchanged.

## 0.2.1 (2026-11-26)

- Fixed: `SQLiteStore` could fail with "database is locked" when several processes or threads opened a brand-new database file at the same moment (about 1 in 27 at 16 at once), because SQLite does not wait while switching to WAL mode. Setup now retries within `timeout`. This was the intermittent CI failure.
- README and PyPI page: Tenkyu is published (`pip install tenkyu`); the status is now "Early Access".
- Tests: the huge-`Forwarded`-header test checked a fixed 2-second limit, which failed at random on slow CI machines. It now checks that parsing time grows linearly with input size. Thread-based tests report a thread's real error instead of a count mismatch, and wait longer for SQLite locks.
- CI runs every Python version even when one fails and posts failing test names as annotations on the run page.

## 0.2.0 (2026-11-26)

Defenses from the 2026-11-26 attack run. Existing integrations behave the same unless they opt in; the benchmark is unchanged (F1 0.82, 3.7% of real users to review, none blocked).

- Yahoo, ymail.com and rocketmail.com hyphen aliases (`name-anything@yahoo.com`) collapse to one address. Zero-width characters are removed from emails before matching.
- The owner of an address is no longer blocked because someone signed up earlier with an alias of it: the plain address after only aliases gets `owner_after_aliases` (score 0) instead of `alias_reuse`. A repeat of the plain address, or an alias after it, is still blocked.
- `Signup(links={...})`: up to 8 stable ids (card fingerprint, verified phone, OAuth id). Accounts sharing one get `link_reuse` (0.9). Values are stored as the first 32 hex characters of their SHA-256; bad names or values raise `ValueError` before anything is written.
- New `network_burst` (5+ signups from one IPv4 /24 in 10 minutes, 0.4) and `network_day` (4+ in a day 0.15, 10+ 0.4) signals catch farms that rotate addresses inside one network. A 9-person office over a working day stays allowed.
- `Guard(starter_fraction=..., surge_threshold=..., shadow=...)`, all off by default. `Decision` gains `limit` and `shadow_action`, included in `to_dict()` only when set.
- `DecisionLog(path)` and `Guard(log=...)`: one JSON line per recorded decision, with the email as a 16-hex SHA-256 prefix and no raw email, IP or device id. A failing log never breaks signup; dry runs are not logged. In shadow mode `Decision` also carries `would_credit_fraction` and `would_limit`.
- `python -m tenkyu report decisions.jsonl [--grant 3] [--json]`: totals by would-be action, repeat inboxes, top reasons, and free grants withheld from flagged signups, reported apart from credits held from allowed users until they verify. Unreadable lines are skipped and counted.
- `python -m tenkyu audit signups.csv [--grant 3] [--out flagged.csv] [--link card=column] [--json]`: replays your own signup export in time order, offline, and reports how many signups Tenkyu would flag and the free credits withheld. Unsorted exports, ISO or epoch times and common column names work; rows without a readable time are counted and skipped. On the benchmark data it reproduces the benchmark's recall.
- `tenkyu.webhooks`: `verify_webhook(secret, headers, body)` for Svix (Clerk) and Standard Webhooks (Supabase) signatures with a 5-minute window, checked against the published spec vector; `signup_from_clerk(event)` and `signup_from_supabase(payload)` build a `Signup`, passing a verified phone and OAuth ids as `links`.
- `Guard.for_ai_apps(**overrides)`: recommended settings for AI apps (starter_fraction 0.5, surge_threshold 25). The benchmark adds a grants-received table for the default, this preset and the preset with a card link, with the honest-user cost stated (`docs/benchmark-economics.json`).
- `tenkyu audit --sample` runs on a bundled synthetic export (939 signups, shipped as package data). More column names are recognized (`dev`, `ua`, `primary_email_address`, `created (utc)`, `inserted_at` and others), and columns the audit did not use are listed. The README now opens with the audit.
- Fixed: the owner of a Gmail address written with dots (`maya.cohen@gmail.com`) was treated as an alias when a squatter had used `maya.cohen+promo@` first. An address now counts as the owner's when it has no `+tag` (or Yahoo `-keyword`); dot-only variants still count as reuse. The store now keeps only whether an address was plain or tagged, never the raw address.
- Fixed: `tenkyu audit --sample --json` printed a notice before the JSON.
- `scripts/release_check.sh`: tests, wheel build, wheel contents (sample CSV in, tests out), clean install and a CLI smoke run. `docs/friend-trial.md`: a two-week shadow-mode trial kit. The Show HN draft leads with the audit.
- The dashboard's browser engine is checked against this library on shared scenarios (`tests/test_engine_parity.py`); the first run found that it labelled alias and shared-card accounts `allow`, now fixed.
- `import tenkyu` no longer needs `sqlite3`: `SQLiteStore` is imported on first use, so the library runs on Pythons built without it (Pyodide, slim containers). Found by running Tenkyu in the browser.
- `requires-python` is now `>=3.11`, matching what is tested (3.11, 3.12, 3.13); 3.9 and 3.10 were claimed but never tested. README links are absolute GitHub URLs so they work on the PyPI page.
- The README demo's last row scores 1.00 instead of 0.99 (same action).

## 0.1.0 (unreleased)

First version. Not published to PyPI yet.

- `client_ip` (and `signup_from_request`) now also reads the standard `Forwarded: for=` header when `trusted_proxies` is above 0 and there is no `X-Forwarded-For`, counted from the right the same way. Before this, a proxy that sends only `Forwarded` made every visitor look like the proxy's address (one IP). `X-Forwarded-For` wins when both are present; quoted values, `for="[v6]:port"`, `for=unknown` and obfuscated tokens are handled (those fall back to the socket address). The default `trusted_proxies=0` still ignores both headers.
- New `tenkyu.testing.StoreConformance`: the store contract as reusable tests, so a Redis or Postgres store can prove it behaves like the built-in ones, including that `transaction()` is atomic. `tests/test_conformance.py` runs it against `MemoryStore`, `SQLiteStore` and a dict-backed store, and checks that it fails for stores that are wrong. No change for existing users.
- `client_ip` accepts forwarded entries that carry a port (`198.51.100.7:51234`, `[2001:db8::7]:443`), as Azure Application Gateway and IIS append. Before this such an entry was not recognized as an address, so Tenkyu fell back to the proxy's own address and every visitor behind it looked like one IP. An unbalanced bracket (`[::1`) is no longer accepted as an address. `SQLiteStore("")` now raises `ValueError` (SQLite would have used a throwaway temporary database and silently never persisted anything).
- `SQLiteStore(path, timeout=5.0)`: how long to wait for another writer's lock before raising `sqlite3.OperationalError` (was fixed at 5 s; must be a positive number). The sweep when a file is opened is now best-effort and never waits: before this, opening a store while another process held the write lock waited 5 s and then failed. `check` still raises on a lock timeout and never silently allows.
- `Guard.check` now reads the history and records the signup as one atomic step (`store.transaction()`: a lock for `MemoryStore`, `BEGIN IMMEDIATE` for `SQLiteStore`). Before this, many aliases of one person sent in parallel all passed the alias check: 16 parallel signups let in 7.5 on average (up to 13) through a shared `SQLiteStore`, and 6 of 6 across 6 processes; a custom store without `transaction()` still works but is only protected within one process. Signups on one store now run one at a time; `record=False` dry runs are unaffected. Scores do not change.
- New `ip_key(ip)`: the address as Tenkyu keys it in the store (IPv6 by /64, mapped IPv4 as IPv4, long strings hashed). Custom signals that read the store must use it: the documented `store.count(f"ip:{signup.ip}", ...)` pattern silently stopped matching IPv6 clients once IPv6 counting by /64 landed (found by running the docs). `docs/signals.md` now uses `ip_key`; the store key names (`ip:`, `email:`, `ipstem:`, `devemail:`) are otherwise unchanged.
- Expired history is now actually forgotten. Before this, an email, IP or device that never signed up again was never removed, so `MemoryStore` memory and the `SQLiteStore` file grew without limit in a long-running process (in a test, 40 days after the last signup all 20,000 keys were still held). Both stores now sweep expired events as they go (after as many adds as keys left by the last sweep, at least 1000, so the cost per add stays flat) and `SQLiteStore` also sweeps when it opens a file, and stored data stays within about twice the live set. `SQLiteStore` adds an index on `ts` the first time it opens an existing file. Scores do not change.
- `device_id` and `ip` strings longer than 128 characters are stored as their SHA-256, so equal long values still match each other. Before this, a client that controls `device_id` could make every signup cost hundreds of KB: 100 signups with 100 KB values took 30 MB of memory or 58 MB of SQLite file, and now take 0.4 MB of memory or about 4 MB of SQLite files (mostly page overhead from 100 separate commits). Scores for normal-length values do not change.
- Email domains with a trailing dot (`john@gmail.com.`, `x@mailinator.com.`) are now treated as the same mailbox and the same disposable domain. Before this, the trailing dot dodged both the Gmail alias collapse and the disposable-domain list. An address like `a@b.` (nothing after the dot) is now invalid.
- IP counting now treats an IPv6 network (/64) as one IP and `::ffff:a.b.c.d` as `a.b.c.d`. Before this, 10 signups rotating through addresses of one IPv6 network were all allowed, while the same 10 from one IPv4 address were blocked from the third. This changes scores for IPv6 traffic; IPv4 and the benchmark are unchanged.
- `python -m tenkyu score --db PATH` prints one line and exits 3 when the database cannot be opened (missing folder, a directory, not a SQLite file) instead of a Python traceback. `SQLiteStore(None)` now raises `TypeError` instead of silently creating a file named `None`.
- `Guard.check(Signup)` returns an explainable `Decision`: action (`allow`, `review`, `block`), score, reasons, signals and `credit_fraction`.
- Nine signals: alias reuse, disposable email, IP burst, IP velocity, lookalike emails from one IP, device reuse, automation user agent, missing user agent, invalid email.
- `MemoryStore` (thread-safe, per process) and `SQLiteStore` (survives restarts, shared by processes on one machine).
- `signup_from_request` and `client_ip` with an explicit `trusted_proxies` setting.
- `load_domains` for a disposable-domain list you download yourself; a small starter list is bundled.
- Graduated credit unlock through `credit_fraction`.
- `python -m tenkyu demo | score | version`; `score` exits 0 for allow, 10 for review, 20 for block.
- A synthetic benchmark (`benchmarks/farming_bench.py`). It uses data we generated, so it does not measure real-world accuracy.
- FastAPI and Flask examples. They compile but have not been run against the live frameworks.
- Tested on Python 3.11 and 3.13.
- A custom signal that returns something other than a well-formed `Signal` is now ignored instead of raising out of `check`. `docs/signals.md` explains how to write one.
- Fixed before release: the default stores kept events for 1 day while the device check looks back 7 days, so a fourth account on one device could look like a second. Default retention is now 30 days.
- A shared device id alone no longer reaches `block`: `device_reuse` scores 0.65 for three or more accounts (was 0.85), so a household's third account goes to review. In the synthetic benchmark this took real users blocked from 3 to 0 with no change in recall or F1.
